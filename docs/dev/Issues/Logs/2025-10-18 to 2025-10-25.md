I decided to rewrite Hich. I made this decision because of the accumulated technical debt burden that made it extremely difficult to test or reason about.

The new architecture is based on groovy classes as follows:
+ `HichContract`: A collection of maps specifying process inputs, outputs, commands, and sample key validation and transformations.
+ `HichEngine`: Responsible for invoking sample key validation and transformation, and process command and output building.
+ `HichExecutionContextBuilder`: Implements specific command and output builders (execution contexts).
+ `HichValidator`: Implements specific sample key validation rules.
+ `HichTransformer:` Implements specific sample key transformation rules.
+ `HichWorkflowAdapter`: Adapters between Nextflow and groovy classes.
+ `HichUtil`: Common, non-Nextflow utility functions.
+ `HichRuleValidator`: Second utility class, to be merged into HichUtil

The `HichContract` specifies the bulk of how the `HichExecutionContextBuilder` builds process commands and outputs based on relevant sample keys; the `HichExecutionContextBuilder` provides the implementation.

The advantages of this approach include:
+ The contract completely and legibly specifies the behavior of the pipeline separate from implementation. It also permits automated documentation. This is a win for reliability and ease of use.
+ Separation of concerns speeds testing and feature implementation, improving reliability, versatility and power in the long run.

As the heavy lifting is now in groovy rather than nextflow, we can use Spock to automate groovy code testing, which will increase test speed by several orders of magnitude. However, this requires me to learn new technology for building and automated testing:
